chutvrc Evaluation Manual

A step-by-step guide for who is conducting a cross-configuration performance evaluation of chutvrc.

For the harness in eval/. Print-friendly.

1. Overview

The eval harness is a measurement instrument, not an experiment driver. You decide which (hosting × SFU × N) cells to measure, reconfigure chutvrc manually for each, then run the runner once per cell. The runner collects timestamps from in-browser probes and writes CSVs.

The intended sweep covers up to 3 hosting environments × 4 SFU backends for cross-configuration metrics, plus a scalability run at N = 5 / 10 / 20 / 40 / 80 concurrent participants. Live SFU switching is out of scope for this round.

Time budget Each cell = 5 minutes of measurement plus ~5 minutes of setup/teardown. The full matrix (12 RQ1 cells + 5 RQ2 cells per SFU) is roughly half a day of attended work per hosting environment. Plan accordingly.

2. Before the evaluation

2.1 Build & install

From a clean clone of chutvrc-hubs-compose with the harness present:

# Generate the silent carrier WAV for speaker bots (one-time).
node eval/assets/generate-chirp.js

# Build the runner image once. Rebuild only when eval/runner/ changes.
docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml build eval-runner

# Make sure the bot's Puppeteer install actually works on this host.
cd services/hubs && npm install && node scripts/bot/run-bot.js --help && cd -

If Puppeteer's Chromium download is blocked by your network, set PUPPETEER_DOWNLOAD_HOST or install Chromium separately and point Puppeteer at it. Puppeteer must succeed before any bot run.

2.2 Network & clocks

  • Decide where the runner will live. It must be reachable from every measurement participant (real device or bot host) over a WebSocket. On a LAN, this is the runner host's LAN IP or mDNS name (hubs.local). On the public internet, behind a reverse proxy with a TLS cert.
  • Put that hostname/IP into .env as EVAL_REPORT_HOST=<hostname-or-ip>. The compose file uses it to build the join URL.
  • Verify NTP/chrony is running on every host that will participate (runner, bot hosts, ideally the chutvrc server). Sub-millisecond LAN sync is normal; sub-10ms WAN sync is usually fine. The clock-sync CI in run.json will tell you if it was good enough.
  • If you'll have phones/tablets/HMDs on the LAN, ensure their browsers can reach the runner WS port (default 9099). Open the firewall.

2.3 SFU credentials (if measuring beyond Dialog)

  • Create eval/.env.local (gitignored) with credentials for any non-Dialog SFU you'll measure (LiveKit API key/secret, Sora signing key, Cloudflare Realtime app ID + secret).
  • Plumb the same credentials into reticulum's webrtc-settings via the admin panel — this is where the running server actually reads them.
  • Confirm a manual test room with each SFU successfully connects and produces audio/video between two ordinary browsers before measurement starts. The harness measures what it sees; if a backend is misconfigured, you'll get clean-looking but meaningless data.
Billing risk Sora and Cloudflare Realtime are billable. Sanity-check rate limits and budgets in their admin consoles before scaling to N=80. The runner enforces EVAL_ALLOW_BILLING=1 for non-Dialog cells, but human attention is the better safeguard.

2.4 Reticulum config flip (one-time)

To change a room's SFU at runtime, reticulum's webrtc-settings|allow_switch_sfu must be true. If it's currently false in your deployment, flip it once in the admin panel (https://<admin-host>:8989/admin.html) at the start of the eval and revert at the end. No code change required.

2.5 First-time smoke (do this once on your laptop)

Verify the entire pipe end-to-end before committing to a real cell.

1

Start the runner in a throwaway window

docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml \
  run --rm --service-ports eval-runner runner start \
    --label smoke \
    --room https://hubs.local/<any-test-room-sid> \
    --duration 90s \
    --dialog-url http://dialog:7001 \
    --host-stats docker \
    --public-url wss://${EVAL_REPORT_HOST:-hubs.local}:9099

The runner prints a join URL with the eval probe params.

2

Open the printed URL in your laptop browser

Add &label=laptop-self. Open the DevTools console. Within ~10 seconds you should see:

[eval] probe enabled mode=passive label=laptop-self report=wss://…
[eval] clock synced offset=…ms ±…ms

If the clock-sync line never appears, the WebSocket isn't reaching the runner (firewall, wrong hostname, missing TLS). Fix this before going further.

3

Wait for runner exit, then check the CSVs

After 90 s the runner prints [runner] aggregator wrote CSVs to …. In that directory:

  • run.json should list one client with a clock_ci_ms < 5.
  • probe-events.csv should have rtc-stats rows (your laptop's PC stats).
  • Other CSVs may be empty (no peer, no chirps) — that's fine for a self-only smoke.
4

Two-client smoke with a speaker bot

In one window run the runner (same command). In another, launch a single speaker bot pointed at the same room:

cd services/hubs
EVAL_MODE=1 EVAL_LABEL=bot-speaker EVAL_SPEAKER=1 \
EVAL_REPORT_WS_URL=wss://${EVAL_REPORT_HOST:-hubs.local}:9099 \
node scripts/bot/run-bot.js \
  -o ${HUBS_HOST:-hubs.local} \
  -r <room-sid> \
  -a ../../eval/assets/chirp-loop.wav

Join the same room from your laptop browser with ?eval=1&mode=passive&label=laptop-self&report=…. After the run, chirp-pairs.csv should have rows. If it doesn't, the chirp pipeline is broken — see §5 Troubleshooting before going further.

2.6 Plan the matrix

Decide the exact cells you'll measure before you start, including labels. A reproducible label scheme makes post-hoc aggregation trivial. Recommended:

<hosting>+<sfu>+N<count>[+<variant>]
Examples:
  laptop+dialog+N10
  server+livekit+N40
  cloud+sora+N20+devices
  cloud+cloudflare+N80+bots-only

Fill in the matrix tracker at §4 before any measurement run.

2.7 Pre-flight checklist (print and tick)

  • eval/assets/chirp-loop.wav exists (run node eval/assets/generate-chirp.js).
  • chutvrc-eval-runner Docker image builds (docker compose --profile eval … build eval-runner).
  • Bot Puppeteer install works (node scripts/bot/run-bot.js --help exits 0).
  • EVAL_REPORT_HOST set in .env; reachable from every participant device.
  • NTP/chrony running on runner host and bot hosts.
  • webrtc-settings|allow_switch_sfu = true in admin panel.
  • For non-Dialog SFUs: credentials in eval/.env.local AND admin panel; manual two-browser sanity test passed.
  • Self-only smoke test produced a run.json with clock-CI < 5 ms.
  • Two-client smoke (speaker bot + laptop) produced a non-empty chirp-pairs.csv.
  • Matrix tracker filled in: every cell labelled, every label unique.
  • Sufficient bot host capacity for the largest N (~250 MB RAM per headless Chrome).
  • Quiet network on the runner LAN during measurement (no large concurrent transfers).
  • Stopwatch / timer set to 5 min for each measurement (or rely on --duration).

3. During each cell

Repeat for every cell in your matrix. Each cell takes ~10 minutes of attended time.

3.1 Reconfigure the cell (manual)

1

Hosting

If you're switching hosting environment (laptop → server → cloud), redeploy chutvrc on the target host. Verify the deployment is healthy: a normal browser can join a normal room with mic+pose working. This is not the harness's job; trust nothing the harness reports until the underlying deployment is verified.

2

SFU

In the admin panel (https://<admin-host>:8989), open the target room, set the SFU field:

  • 0 Dialog
  • 1 Sora
  • 2 LiveKit
  • 3 Cloudflare Realtime

Confirm by joining the room from one browser and checking the DevTools network tab for the expected SFU's WebSocket/HTTP traffic. Wrong SFU → meaningless data.

3

Room state reset

Kick any leftover participants from previous runs. The runner will refuse to attribute their data, but they'll skew SFU load if they linger. The admin panel has a kick action; alternatively, delete and re-create the room.

3.2 Start the runner

docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml \
  run --rm --service-ports eval-runner runner start \
    --label "laptop+dialog+N40" \
    --room "https://${HUBS_HOST}/<room-sid>" \
    --duration 5m \
    --dialog-url http://dialog:7001 \
    --host-stats docker \
    --public-url "wss://${EVAL_REPORT_HOST}:9099"

The runner stays attached to the terminal; copy the join URL it prints. The 5-minute timer starts now, so move fast.

If the runner won't start Almost always either port 9099 is already in use (another runner not shut down cleanly) or the EVAL profile isn't activated. docker ps to check, docker compose --profile eval … down if needed.

3.3 Launch the speaker

Choose one of: a designated speaker bot, or a designated real-device speaker. Never more than one — chirps from multiple sources cannot be disambiguated.

Option A — bot speaker

cd services/hubs
EVAL_MODE=1 EVAL_LABEL=bot-speaker EVAL_SPEAKER=1 \
EVAL_REPORT_WS_URL="wss://${EVAL_REPORT_HOST}:9099" \
node scripts/bot/run-bot.js \
  -o "${HUBS_HOST}" \
  -r "<room-sid>" \
  -a ../../eval/assets/chirp-loop.wav &

Option B — real-device speaker

Open the runner's join URL on the designated speaker device, replacing &mode=passive with &mode=speaker and &label=<device> with a unique speaker tag (e.g., &label=speaker-laptop). Click anywhere on the page once to unlock audio playback (mobile autoplay policy).

3.4 Launch listener bots (only if your N exceeds your real-device count)

cd services/hubs
# Adjust the count to reach your target N.
for i in $(seq 1 39); do
  EVAL_MODE=1 EVAL_LABEL="bot-listener-$i" \
  EVAL_REPORT_WS_URL="wss://${EVAL_REPORT_HOST}:9099" \
  node scripts/bot/run-bot.js \
    -o "${HUBS_HOST}" \
    -r "<room-sid>" \
    -a ../../eval/assets/chirp-loop.wav &
done

Wait ~30 s for all bots to fully join. The runner logs [runner] hello client_id=… label=bot-listener-N for each one. If you see fewer hellos than bots you launched, some failed — check the bot terminal output.

Multi-host bot distribution At N≥40 you'll likely run out of RAM on one box. SSH the same loop to a second host with the same env vars. The runner correlates them by client_id + label; nothing else changes.

3.5 Bring in real devices

For each device:

  1. Scan the QR / open the runner's join URL.
  2. Edit the URL bar: replace &label=<device> with a unique tag, e.g. quest3-haru, ipad-2-tabA, macbook-3-tabB. Each tab gets a different label.
  3. Click once on the page to unlock audio.
  4. Confirm in the device's browser console (or the runner's terminal) that the probe shows [eval] clock synced.

3.6 Monitor the run

For the full duration, watch:

  • Runner terminal — every connect/disconnect should be expected. Disconnects mid-run usually mean a bot ran out of memory.
  • One representative listener device console — should keep emitting [eval] clock re-validated roughly every 30 s, no error spam.
  • chutvrc deployment health — dialog/reticulum containers should not be OOM-killed or restarting. docker stats or kubectl top pods.

Do not tweak chutvrc, the network, or other clients during the run. A reconfiguration mid-cell invalidates the cell. Mark down anything unusual that happens for your notes.

3.7 Validate & archive

When the runner exits, immediately check the produced eval/results/<run_id>/:

Per-cell validation (do this before starting the next cell)

  • run.json exists. Open it. clients array length equals (speakers + listeners + real devices). If any are missing, that participant's data never reached the runner.
  • Every entry in run.json's clients has clock_ci_ms < 5. Cells with worse CIs may be discarded.
  • No entry has a non-empty warnings array. The most likely warning is "more than one mode=speaker" — if you see it, the cell is contaminated; re-run.
  • pose-pairs.csv line count is roughly N × (N−1) × 4 × 67 × duration_sec × sample_rate. For a 5-min N=10 dialog cell at sample_rate=1, expect ~720,000 rows. Order-of-magnitude is fine.
  • chirp-pairs.csv has roughly (number of listeners) × (duration_sec / 1.5) rows. Below 50% of expected means some listeners weren't hearing the speaker — investigate before trusting the cell.
  • host.csv has rows for at least dialog and reticulum containers (or your equivalent). If empty, --host-stats was wrong.

Rename the result directory if useful (default name is <ISO-timestamp>_<label>, which is already self-describing). Copy or move it to your archival location — these CSVs are the primary source data for whatever analysis or report you produce from this run.

Update the matrix tracker (§4) with the run_id, CI, and any notes.

5. Troubleshooting

Probe never logs "clock synced"

The probe loaded but can't talk to the runner. In order of likelihood:

  • Wrong &report= URL in the join URL. Compare against what the runner printed.
  • Mixed-content blocking: a wss:// page can connect to wss:// runner, but an http:// page cannot connect to ws:// in many browsers. Either everything is TLS or nothing is.
  • Firewall blocking port 9099 on the runner host.
  • If using k8s ingress: certificate not trusted, or websocket-tunnel timeout too short (haproxy default is 60s; set haproxy.org/timeout-tunnel: "30m").

chirp-pairs.csv is empty or sparse

  • No speaker connected, or the speaker died. Check run.json for a client with mode: "speaker".
  • Speaker bot ran without EVAL_SPEAKER=1 — it defaulted to passive and emitted no chirps.
  • Mobile-device speaker without a click-to-unlock-audio gesture. mode=speaker is rarely the right choice for phones/tablets — use bot speakers instead.
  • Goertzel false-negative due to codec degradation. Verify by listening: have a human join the room and confirm they hear the periodic 1 kHz blips from the speaker.

pose-pairs.csv has far fewer rows than expected

  • You used ?sample=<x> on listener URLs and forgot to multiply expectations by x.
  • Bots died mid-run. Check bot terminals for process.exit, OOM, or "Detected avatar dog-pile" — the last should be continuing in EVAL_MODE; if it's Restarting, the bot wasn't launched with EVAL_MODE=1.
  • Receive-side sampling is on. The probe defaults to sample=1.0 (100%). At N ≥ 40 some operators set sample=0.1 to reduce WS bandwidth.

clock_ci_ms is large (> 5)

  • Run a quick LAN ping to the runner host. If RTT itself is > 5 ms, latency-level accuracy is what you have.
  • WiFi vs Ethernet: if the runner is on WiFi, move it to Ethernet for the eval.
  • Background network load on the runner host — pause syncs, large downloads, screen-shares.

Runner immediately exits with "EADDRINUSE"

Port 9099 already taken. lsof -i :9099 (mac/linux) or netstat -ano | findstr 9099 (Windows) to find the holder, kill it, or pass --port 9100 (also update EVAL_REPORT_HOST-derived URLs).

rtc-stats.csv is missing fields for LiveKit / Sora

The probe reaches into adapter internals (_sendTransport, room.engine.publisher.pc, etc.) via known field names. If the upstream adapter changed shape, the PeerConnection list comes back empty. Open services/hubs/src/eval/rtc-stats.ts, function extractPeerConnections, and adjust the field paths to match the current adapter. All other metrics keep working.

6. After all cells

  • Revert the webrtc-settings|allow_switch_sfu flip in the admin panel if your production deployment requires it.
  • Stop and remove any leftover bot processes and runner containers (docker compose --profile eval … down; pkill -f run-bot.js).
  • Archive the entire eval/results/ directory to long-term storage. The CSVs are the primary source data behind any number you'll report; treat them as such.
  • For each figure or summary you produce, fill in the corresponding row of eval/docs/figures-to-commands.md with the run_id and exact CLI used.
  • Run the aggregation snippet in eval/docs/interpreting-results.md over all run.jsons to produce the per-cell summary table.
  • Generate plots from the CSVs using your preferred tool (matplotlib, R, ggplot, Excel).
