chutvrc Evaluation Manual

Step-by-step guide for conducting a cross-configuration performance evaluation of chutvrc.

For the harness in eval/. Print-friendly.

1. Overview

The eval harness is a measurement instrument, not an experiment driver. You choose each (hosting × SFU × N) cell, reconfigure chutvrc manually, then run the eval module once per cell. It collects timestamps from browser agents and writes CSVs.

Intended sweep: 3 hosting environments × 4 SFU backends for cross-config metrics, plus a scalability run at N = 5 / 10 / 20 / 40 / 80. Live SFU switching is out of scope this round.

Time budget Each cell = 5 min measurement + ~5 min setup/teardown. The full matrix (12 RQ1 + 5 RQ2 cells per SFU) is ~half a day of attended work per hosting environment. Plan accordingly.

1.1 Hosts, roles & terminology

The harness involves three host roles plus an browser agent. They can collapse onto one physical machine for small evals, or split across several. Knowing which command runs where is the most common source of confusion — every command block below is tagged accordingly.

TermDefinition
chutvrc server The machine (or k8s cluster) running reticulum, dialog, hubs-client, and any SFU. The system under measurement.
Eval module host The machine that runs the eval-runner Docker container. The eval module is a Node process that opens a WebSocket on port 9099, receives measurement events from every browser agent, polls Dialog and Docker/k8s for server-side stats, and writes the CSVs in eval/results/. Its hostname/IP is set as EVAL_REPORT_HOST and must be reachable over WebSocket from every participant. The eval module does not join the chutvrc room.
Bot user host Any machine that runs node scripts/bot/run-bot.js. Each invocation spawns a headless Chrome via Puppeteer that joins the chutvrc room as a real client. With EVAL_MODE=1 the bot user's page loads the browser agent and reports to the eval module. With EVAL_SPEAKER=1 the bot user emits chirp audio for audio-latency timing; otherwise it's a passive listener. Bot user hosts need an npm installed copy of services/hubs and local access to the chirp WAV.
Real device A phone, tablet, laptop, or HMD that joins through its own browser by opening the eval module's printed join URL. Real devices need no install — only network reachability to chutvrc and to the eval module.
Participant / client Either a bot user or a real device — anything that joins the room and reports to the eval module. The eval module identifies each one by client_id + label.
Browser agent A small JS module shipped inside chutvrc that activates only when the page is loaded with ?eval=1. It clock-syncs with the eval module, samples pose / audio / RTC stats, and ships events over WebSocket. Both bot users (via Puppeteer) and real devices run the same browser agent code.
Cell One (hosting × SFU × N) configuration measured in a single eval module invocation. Each cell yields one eval/results/<run_id>/ directory.
Speaker / Listener Roles a participant can play, set via the browser agent's mode param. Exactly one participant per cell is the speaker (its mic emits 1 kHz chirps used for audio-latency timing); all others are passive listeners.

Recommended topology. For the cleanest measurements use two machines:

  • Machine A: chutvrc server and eval module host on the same box. The eval module is a passive WebSocket collector and is lightweight; co-locating it with chutvrc also lets --host-stats docker read container stats locally without remote-Docker auth.
  • Machine B: bot user host — runs the speaker bot user and any listener bot users. Never run bot users on the chutvrc host. Co-located bot users (a) contend for CPU/RAM with chutvrc and corrupt host.csv; (b) talk to chutvrc over localhost / the Docker bridge, which is not a realistic client network path; (c) share a kernel clock with the eval module, producing artificially perfect clock-sync that biases cross-client latency arithmetic.

Collapsing everything onto one machine works for the very first smoke test (§2.4) but should not be used for any measured cell. At N ≥ 40 you'll likely need more than one bot user host — see the §3.4 multi-host callout, and ideally dedicate one bot user host to the speaker so listener bot user CPU pressure doesn't smear chirp-emit timestamps. Real devices are never the same machine as any of the above.

Command-block tags. Every command block in this manual is tagged with the host it runs on:

  • Run on: eval module host — the box that will host the eval-runner Docker container.
  • Run on: bot user host — every box that will launch run-bot.js.
  • Run on: any host — one-off setup that just needs to land on disk somewhere; copy the output to where it's actually needed.

Never run any of these commands on a real device (phone/tablet/HMD). Real devices only open URLs in a browser.

2. Before the evaluation

2.1 Build & install

Each command below targets a specific host role. From a clean clone of chutvrc-hubs-compose with the harness present:

Generate the silent carrier WAV for speaker bot users (one-time)

Run on: any host
node eval/assets/generate-chirp.js

Writes eval/assets/chirp-loop.wav. The file is needed wherever a speaker bot user runs (passed via -a); if your bot user host is a different machine from where you generated it, copy the WAV over or re-run the script there.

Build the eval-runner Docker image

Run on: eval module host
docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml build eval-runner

Build once. Rebuild only when files under eval/runner/ change.

Verify the bot user's Puppeteer install

Run on: every bot user host
cd services/hubs/scripts/bot && npm install && node run-bot.js --help && cd -

Repeat on every machine that will launch run-bot.js (e.g. each box you split bot users across at large N). If Puppeteer's Chromium download is blocked, set PUPPETEER_DOWNLOAD_HOST or install Chromium separately and point Puppeteer at it. Puppeteer must succeed before any bot user run.

2.2 Network & clocks

  • Decide where the eval module lives. It must be reachable from every participant (real device or bot user host) over a WebSocket. On LAN: eval module host's LAN IP or mDNS name (hubs.local). On public internet: behind a reverse proxy with a TLS cert.
  • Set EVAL_REPORT_HOST=<hostname-or-ip> in .env; the compose file uses it to build the join URL.
  • Verify NTP/chrony runs on every participating host (eval module, bot user hosts, ideally the chutvrc server). Sub-ms LAN sync is normal; sub-10ms WAN sync is usually fine. The clock-sync CI in run.json confirms whether it was good enough.
  • For phones/tablets/HMDs on the LAN, ensure their browsers can reach the eval module WS port (default 9099). Open the firewall.

2.3 SFU credentials (if measuring beyond Dialog)

  • Create eval/.env.local (gitignored) with credentials for each non-Dialog SFU (LiveKit API key/secret, Sora signing key, Cloudflare Realtime app ID + secret).
  • Plumb the same credentials into reticulum's webrtc-settings via the admin panel — that's where the running server reads them.
  • Before measuring, confirm a manual test room with each SFU connects and produces audio/video between two ordinary browsers. The harness measures what it sees; a misconfigured backend yields clean-looking but meaningless data.
Billing risk Sora and Cloudflare Realtime are billable. Sanity-check rate limits and budgets in their admin consoles before scaling to N=80. The eval module requires EVAL_ALLOW_BILLING=1 for non-Dialog cells, but human attention is the better safeguard.

2.4 First-time smoke (do this once on your laptop)

Verify the pipe end-to-end before committing to a real cell.

1

Start the eval module in a throwaway window

Run on: eval module host
docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml \
  run --rm --service-ports eval-runner start \
    --label smoke \
    --room https://hubs.local:4000/<any-test-room-sid> \
    --duration 90s \
    --dialog-url http://dialog:7001 \
    --host-stats docker \
    --public-url wss://${EVAL_REPORT_HOST:-hubs.local}:9099

The eval module prints a join URL with the browser agent params. Port 4000 in --room is the local hubs dev server; for a deployed hubs behind TLS use that origin instead (typically port 443, omittable). Port 9099 in --public-url is the eval runner's report WebSocket (always 9099 regardless of how hubs is hosted).

2

Open the printed URL in your laptop browser

The printed URL contains &label=<device>; replace <device> with laptop-self. Open the DevTools console. Within ~10 s you should see:

[eval] probe enabled mode=passive label=laptop-self report=wss://…
[eval] clock synced offset=…ms ±…ms

If the clock-sync line never appears, the WebSocket isn't reaching the eval module (firewall, wrong hostname, missing TLS). Fix before continuing.

3

Wait for eval module exit, then check the CSVs

After 90 s the eval module prints [runner] aggregator wrote CSVs to …. In that directory:

  • run.json should list one client with clock_ci_ms < 5.
  • probe-events.csv should have rtc-stats rows (your laptop's PC stats).
  • Other CSVs may be empty (no peer, no chirps) — fine for a self-only smoke.
4

Two-client smoke with a speaker bot user

Start order matters: launch the eval module first (so the report WS is up), then the bot, then the laptop browser. The bot's probe opens its WS at page-load and won't retry on failure.

In one window on the eval module host, run the eval module (same command as step 1). In another window on a bot user host, launch a speaker bot user pointed at the same room:

Run on: bot user host
cd services/hubs
EVAL_MODE=1 EVAL_LABEL=bot-speaker EVAL_SPEAKER=1 \
EVAL_REPORT_WS_URL=wss://${EVAL_REPORT_HOST:-hubs.local}:9099 \
node scripts/bot/run-bot.js \
  -o ${HUBS_HOST:-hubs.local:8080} \
  -r <room-sid> \
  -a ../../eval/assets/chirp-loop.wav

-o takes the hubs origin including the port for the host that serves /hub.html (the bot builds the URL as https://<host>/hub.html). In the docker-compose dev stack that's port 8080 (the hubs-client webpack dev server), not port 4000 (reticulum, which serves room-SID URLs to browsers but returns 404 for /hub.html). For local dev: -o hubs.local:8080 (or export HUBS_HOST=hubs.local:8080). For deployed setups, use whatever single origin serves both /hub.html and the room SID routes.

Join the same room from your laptop browser with ?eval=1&mode=passive&label=laptop-self&report=…. Click at least once on the room page (the lobby/entry sequence already involves clicks) — Chrome's autoplay policy keeps the chirp detector's AudioContext suspended until the first user gesture, so a passive "open URL and wait" tab will produce chirp-detect = 0. After the run, both laptop-self|chirp-detect rows in probe-events.csv and chirp-pairs.csv should be non-empty. If empty, the chirp pipeline is broken — see §5 Troubleshooting before continuing.

Quick mid-run sanity check (DevTools console on the laptop tab, while the runner is still counting down):

__eval.patcher._detector._ctx.state              // expect "running"
__eval.patcher._detector._activeDetectors.size   // expect >= 1 (one per remote audio peer)

2.5 Plan the matrix

Decide every cell and its label before starting. A reproducible label scheme makes post-hoc aggregation trivial. Recommended:

<hosting>+<sfu>+N<count>[+<variant>]
Examples:
  laptop+dialog+N10
  server+livekit+N40
  cloud+sora+N20+devices
  cloud+cloudflare+N80+bots-only

Fill in the matrix tracker at §4 before any measurement.

2.6 Network choice (methodological note)

Network is not a controlled axis in the matrix; treat it as an implicit constant:

  1. One network per cell, all participants on it (bot users, real devices, eval module). Mixing networks bundles multiple paths into every latency row and prevents attributing cell-to-cell differences to the matrix dimension that varied — most SFUs also adapt to the worst client, so per-client slicing stays confounded.
  2. Same network across all matrix cells. Use the most reliable available (typically campus-affiliated LAN; avoid guest WiFi, which often blocks UDP/STUN/TURN and breaks WebRTC).
Realism vs. control. A controlled matrix on one LAN gives best-case numbers, not what a geographically distributed deployment would see. Don't contaminate the main matrix — run 1–2 supplementary "ecological" cells alongside it (typically for the cloud hosting environment) with participants spread across home / campus / guest networks, and report them separately. Aim for representative coverage, not perfect balance. Label devices by network (mac-home-1, iphone-campus-2) so you can post-hoc slice pose-pairs.csv into home↔home, home↔campus, etc.

Within-cell hygiene: every participant must reach both chutvrc and the eval module (same-network cells avoid public-DNS/TLS/VPN setup); prefer Ethernet on every host that can take a cable; run cells close in time to avoid background-load drift.

Record per cell (matrix notes or label suffix — +campus, +home, +mixed): client network, medium mix, time of day.

Record per network (once, idle, before any measured cell on it — these contextualise the latency numbers):

PropertyHow to retrieve
Name / medium / link standardSSID + WiFi standard (e.g. campus-eduroam, 802.11ax 5GHz) or wired link speed. macOS: system_profiler SPAirPortDataType. Linux: nmcli dev wifi, ethtool eth0.
Baseline RTT to chutvrc and to eval module (mean / min / max / stddev)ping -c 30 <host>
Path + per-hop lossmtr -rwc 30 <chutvrc-host> (or plain traceroute)
Up / down throughputiperf3 -c <server> if you control both ends; otherwise speedtest-cli for a consumer-grade estimate.
UDP allowed (+ jitter, loss)iperf3 -c <server> -u -b 5M. If UDP is blocked, WebRTC falls back to TURN-over-TCP and latencies rise substantially — flag this prominently.
STUN / TURN reachability + NAT typeOpen https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/ — confirm srflx (STUN) and relay (TURN) candidates appear.
External public IP / ISP / approx. geocurl ifconfig.me, plus a lookup (e.g. ipinfo.io/<ip>) for the ISP and rough location.

In-flight per-stream RTT, jitter, and packet loss are captured per cell in rtc-stats.csv automatically. The idle measurements above let you separate "the SFU is slow" from "this network is slow."

State as a limitation in the report: matrix cells are network-controlled (a lower bound on latency); ecological cells indicate the realistic range; production performance depends on each user's path.

2.7 Pre-flight checklist (print and tick)

  • eval/assets/chirp-loop.wav exists (run node eval/assets/generate-chirp.js).
  • chutvrc-eval-runner Docker image builds (docker compose --profile eval … build eval-runner).
  • Bot user Puppeteer install works (node scripts/bot/run-bot.js --help exits 0).
  • EVAL_REPORT_HOST set in .env; reachable from every participant device.
  • NTP/chrony running on eval module host and bot user hosts.
  • chutvrc deployment path identified and tested for every hosting environment in the matrix (see §3.1 for per-cell-type references).
  • For non-Dialog SFUs: credentials in eval/.env.local AND admin panel; manual two-browser sanity test passed.
  • Self-only smoke produced a run.json with clock-CI < 5 ms.
  • Two-client smoke (speaker bot user + laptop) produced a non-empty chirp-pairs.csv.
  • Matrix tracker filled in: every cell labelled, every label unique.
  • Bot user host capacity sufficient for the largest N (~250 MB RAM per headless Chrome).
  • Quiet network on the eval module LAN during measurement (no large concurrent transfers).
  • Stopwatch / timer set to 5 min per measurement (or rely on --duration).

3. During each cell

Repeat for every matrix cell. Each cell takes ~10 min of attended time.

3.1 Reconfigure the cell (manual)

1

Hosting / deployment

Bring chutvrc up on the target host using the deployment path that matches the cell type (table below). Verify health: a normal browser joins a normal room with mic+pose working. This is not the harness's job; trust no harness output until the deployment is verified.

Cell typeRequired setupReference
laptop+* docker-compose on a local host MANUAL_SETUP.md, SSL_SETUP.md, start-{linux,mac,windows}.{sh,command,bat}
server+* docker-compose on an on-prem Linux server MANUAL_SETUP.md, SSL_SETUP.md
cloud+* (compose) docker-compose on a cloud VM MANUAL_SETUP.md, SSL_SETUP.md
cloud+*+k8s k8s cluster (e.g. AKS), manifest deploy; ingress + TLS; dialog pod with hostNetwork and ANNOUNCED_IP matching the node's public IP k8s/docs/OVERVIEW.md, k8s/docs/BUILD_AND_DEPLOY.md, k8s/docs/COTURN_WEBRTC_FIX_PLAN.md

For trade-offs between the two deployment paths and the recommended cell layout, see eval/docs/deployment-comparison.md.

2

SFU

In the admin panel (https://<admin-host>:8989), open the target room and set the SFU field:

  • 0 Dialog
  • 1 Sora
  • 2 LiveKit
  • 3 Cloudflare Realtime

Confirm by joining from one browser and checking DevTools Network for the expected SFU's WebSocket/HTTP traffic. Wrong SFU → meaningless data.

3

Room state reset

Kick any leftover participants from previous runs. The eval module refuses to attribute their data, but they skew SFU load if they linger. Use the admin panel's kick action, or delete and re-create the room.

3.2 Start the eval module

Run on: eval module host
docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml \
  run --rm --service-ports eval-runner start \
    --label "laptop+dialog+N40" \
    --room "https://${HUBS_HOST}/<room-sid>" \
    --duration 5m \
    --dialog-url http://dialog:7001 \
    --host-stats docker \
    --public-url "wss://${EVAL_REPORT_HOST}:9099"

The eval module stays attached to the terminal; copy the join URL it prints. The 5-min timer starts now — move fast.

If the eval module won't start Almost always: port 9099 in use (previous eval module not shut down cleanly) or EVAL profile not activated. docker ps to check; docker compose --profile eval … down to fix.

3.3 Launch the speaker

Choose one: a designated speaker bot user, or a real-device speaker. Never more than one — chirps from multiple sources cannot be disambiguated.

Option A — bot user speaker (recommended for cleanest cells)

Run on: bot user host — a machine separate from the chutvrc / eval module host
cd services/hubs
EVAL_MODE=1 EVAL_LABEL=bot-speaker EVAL_SPEAKER=1 \
EVAL_REPORT_WS_URL="wss://${EVAL_REPORT_HOST}:9099" \
node scripts/bot/run-bot.js \
  -o "${HUBS_HOST}" \
  -r "<room-sid>" \
  -a ../../eval/assets/chirp-loop.wav &
Do not launch the speaker bot user on the chutvrc / eval module host. Co-locating it (i) makes host.csv measure the bot user's CPU/RAM as chutvrc load, (ii) shortcuts the bot user's WebRTC traffic onto localhost — not representative of any real client's network path, and (iii) gives the bot user artificially perfect clock-sync with the eval module (shared kernel clock), biasing every cross-client latency. Use a different machine — even a laptop is enough for a single bot user (~250 MB RAM). At N ≥ 40, give the speaker its own bot user host so listener bot user CPU pressure doesn't delay chirp-emit timestamps.

Option B — real-device speaker

On the speaker device (a real phone/laptop/etc., not a host running any of the commands above), open the eval module's join URL, replacing &mode=passive with &mode=speaker and &label=<device> with a unique speaker tag (e.g. &label=speaker-laptop). Click anywhere once to unlock audio playback (mobile autoplay policy).

3.4 Launch listener bot users (only if your N exceeds your real-device count)

Run on: bot user host (split across multiple at N ≥ 40)
cd services/hubs
# Adjust the count to reach your target N.
for i in $(seq 1 39); do
  EVAL_MODE=1 EVAL_LABEL="bot-listener-$i" \
  EVAL_REPORT_WS_URL="wss://${EVAL_REPORT_HOST}:9099" \
  node scripts/bot/run-bot.js \
    -o "${HUBS_HOST}" \
    -r "<room-sid>" \
    -a ../../eval/assets/chirp-loop.wav &
done

Wait ~30 s for all bot users to join. The eval module logs [runner] hello client_id=… label=bot-listener-N for each. Fewer hellos than launched bot users → some failed; check bot user terminal output.

Multi-host bot user distribution At N≥40 you'll likely run out of RAM on one box. SSH the same loop to a second host with the same env vars. The eval module correlates by client_id + label; nothing else changes.

3.5 Bring in real devices

For each device:

  1. Scan the QR / open the eval module's join URL.
  2. Edit the URL bar: replace &label=<device> with a unique tag (e.g. quest3-haru, ipad-2-tabA, macbook-3-tabB). Each tab gets a different label.
  3. Click once on the page to unlock audio.
  4. Confirm in the device's browser console (or eval module terminal) that the browser agent shows [eval] clock synced.

3.6 Monitor the run

Throughout the run, watch:

  • Eval module terminal — every connect/disconnect should be expected. Mid-run disconnects usually mean a bot user ran out of memory.
  • One representative listener console — should emit [eval] clock re-validated ~every 30 s, no error spam.
  • chutvrc deployment health — dialog/reticulum containers should not OOM-kill or restart. docker stats or kubectl top pods.

Do not tweak chutvrc, the network, or other clients during the run. Mid-cell reconfiguration invalidates the cell. Note anything unusual.

3.7 Validate & archive

When the eval module exits, immediately check eval/results/<run_id>/:

Per-cell validation (do this before starting the next cell)

  • run.json exists. clients array length equals (speakers + listeners + real devices). Missing entries → that participant's data never reached the eval module.
  • Every clients entry has clock_ci_ms < 5. Worse CIs may be discarded.
  • No entry has a non-empty warnings array. The likely warning is "more than one mode=speaker" — if seen, the cell is contaminated; re-run.
  • pose-pairs.csv row count ≈ N × (N−1) × 4 × 67 × duration_sec × sample_rate. A 5-min N=10 dialog cell at sample_rate=1 → ~720,000 rows. Order-of-magnitude is fine.
  • chirp-pairs.csv rows ≈ (listener count) × (duration_sec / 1.5). Below 50% of expected → some listeners weren't hearing the speaker; investigate before trusting the cell.
  • host.csv has rows for at least dialog and reticulum (or your equivalent). Empty → --host-stats was wrong.

Rename the result directory if useful (default <ISO-timestamp>_<label> is already self-describing). Copy or move it to archival storage — these CSVs are the primary source data for any analysis or report.

Update the matrix tracker (§4) with run_id, CI, and notes.

5. Troubleshooting

Browser agent never logs "clock synced"

The browser agent loaded but can't reach the eval module. Likely causes, in order:

  • Wrong &report= URL. Compare against the eval module's printed URL.
  • Mixed-content blocking: an https:// page can only open wss://, and an http:// page can only open ws://. Either everything is TLS or nothing is. The eval-runner reads EVAL_TLS_CERT / EVAL_TLS_KEY at startup; docker-compose.eval.yml defaults them to /certs/cert.pem + /certs/key.pem (mounted from services/hubs/certs/) so local dev gets wss:// automatically. Confirm [runner] report WS listening on wss://… in the runner's first lines; if it logs (no TLS) instead, the cert paths weren't readable.
  • Browser doesn't trust the cert at wss://<runner-host>:9099. If your hubs page loads without a warning, mkcert's root CA is already trusted — the same cert should validate on 9099. Otherwise, visit https://<runner-host>:9099/ once to accept the cert (you'll see "Upgrade Required" — that's fine, the exception is what matters).
  • CSP blocks the report origin. Reticulum sets a strict Content-Security-Policy header on the hub page; connect-src must include wss://<runner-host>:9099 or the browser refuses to open the WebSocket (DevTools shows "Connecting to '…' violates the following Content Security Policy directive: 'connect-src …'"). For local dev this is added in services/reticulum/config/dev.exs (the websocket_hosts string) — restart reticulum to apply. For deployed setups, add the runner's URL via reticulum's admin config (RetWeb.Plugs.AddCSP custom rules).
  • Firewall blocking port 9099 on the eval module host.
  • k8s ingress: untrusted certificate, or websocket-tunnel timeout too short (haproxy default 60 s; set haproxy.org/timeout-tunnel: "30m").

chirp-pairs.csv is empty or sparse

  • No speaker connected, or the speaker died. Check run.json for a client with mode: "speaker".
  • Speaker bot user ran without EVAL_SPEAKER=1 — defaulted to passive, emitted no chirps.
  • Mobile speaker without a click-to-unlock-audio gesture. mode=speaker rarely suits phones/tablets — prefer bot user speakers.
  • Goertzel false-negative from codec degradation. Verify by listening: a human joins the room and confirms they hear the periodic 1 kHz blips.
  • Audible chirps but chirp-detect = 0 (emit count looks normal in probe-events.csv but detect count is zero on every listener). The detector's AudioContext is suspended by Chrome's autoplay policy. The probe auto-resumes on the first pointerdown/keydown/touchstart/click, so a listener tab that's only "opened and observed" without any click stays in this failure mode. Click anywhere on the room page once and re-run. Verify mid-run with __eval.patcher._detector._ctx.state === "running".

pose-pairs.csv has far fewer rows than expected

  • You used ?sample=<x> on listener URLs and forgot to scale expectations by x.
  • Bot users died mid-run. Check bot user terminals for process.exit, OOM, or "Detected avatar dog-pile" — the last should be continuing in EVAL_MODE; if Restarting, the bot user wasn't launched with EVAL_MODE=1.
  • Receive-side sampling on. Browser agent defaults to sample=1.0 (100%); at N ≥ 40 some operators set sample=0.1 to reduce WS bandwidth.

clock_ci_ms is large (> 5)

  • LAN-ping the eval module host. RTT > 5 ms → latency-level accuracy is what you have.
  • If the eval module is on WiFi, move it to Ethernet for the eval.
  • Background network load on the eval module host — pause syncs, large downloads, screen shares.

Eval module immediately exits with "EADDRINUSE"

Port 9099 already taken. Find the holder with lsof -i :9099 (mac/linux) or netstat -ano | findstr 9099 (Windows); kill it, or pass --port 9100 (also update EVAL_REPORT_HOST-derived URLs).

rtc-stats.csv is missing fields for LiveKit / Sora

The browser agent reaches into adapter internals (_sendTransport, room.engine.publisher.pc, etc.) via known field names. If the upstream adapter changed shape, the PeerConnection list is empty. Edit extractPeerConnections in services/hubs/src/eval/rtc-stats.ts to match the current adapter's field paths. Other metrics keep working.

8. Notes & scope decisions

Runtime SFU switching is out of scope

This evaluation does not exercise live SFU switching mid-room. Each cell is measured with a single SFU configured in reticulum before the eval module starts; switching to a different SFU is done by reconfiguring the room (see §3.1) and starting a fresh cell, not by toggling at runtime. As a consequence:

  • The reticulum webrtc-settings|allow_switch_sfu flag is irrelevant for this evaluation and does not need to be flipped or reverted.
  • No mid-run reconfiguration logic in chutvrc is exercised by these measurements; the data characterises steady-state behaviour per (hosting, SFU, N) cell only.

For the harness API surface and CSV column legend see eval/docs/README.md and eval/docs/interpreting-results.md.
