chutvrc 評価マニュアル

chutvrc の異なる構成間の性能評価を実施するための手順書。

評価モジュールは eval/ に格納。

1. 概要

本評価モジュールは計測のためのツールであり、実験を自動実行する仕組みではない。各 (ホスティング × SFU × N) セルは手動で選択し、chutvrc を再構成したうえで、セルごとに 1 回評価モジュールを起動する。評価モジュールはブラウザエージェントからタイムスタンプを収集し CSV に書き出す。

想定する評価範囲: クロス構成指標として 3 種類のホスティング環境 × 4 種類の SFU バックエンド、加えてスケーラビリティ評価として N = 5 / 10 / 20 / 40 / 80。稼働中の SFU 切替は今回対象外。

所要時間の見積もり 1 セル = 計測 5 分 + 準備・片付け 約 5 分。全マトリクス (SFU 1 種につき RQ1 が 12 セル + RQ2 が 5 セル) はホスティング環境 1 つあたり半日程度の手作業となる。スケジュールを確保すること。

1.1 ホスト・ロール・用語

評価モジュールには 3 種類のホストに加え、ブラウザエージェントが存在する。小規模評価では 1 台に統合してもよいし、複数台に分散することもできる。「どのコマンドをどこで実行するか」が最も多いトラブル原因のため、本マニュアル中のコマンド枠にはすべて実行先を明示する。

用語 定義
chutvrc サーバ reticulum、dialog、hubs-client、および SFU を稼働させるマシン (または k8s クラスタ)。評価対象システム。
評価モジュールホスト eval-runner Docker コンテナを稼働させるマシン。評価モジュールはポート 9099 で WebSocket を待ち受け、各ブラウザエージェントから計測イベントを受信し、Dialog および Docker/k8s からサーバ側統計をポーリングし、eval/results/ に CSV を書き出す Node プロセス。ホスト名/IP は EVAL_REPORT_HOST で指定し、全参加者から WebSocket で到達可能でなければならない。評価モジュール自体は chutvrc のルームに参加しない。
ボットユーザーホスト node scripts/bot/run-bot.js を実行するマシン。1 回の呼び出しごとに Puppeteer 経由でヘッドレス Chrome が起動し、通常のクライアントとして chutvrc のルームに参加する。EVAL_MODE=1 を指定するとブラウザエージェントが有効になり、評価モジュールへ報告する。EVAL_SPEAKER=1 を指定すると音声レイテンシ計測用のチャープを送出する (指定しなければパッシブリスナー)。ボットユーザーホストには npm install 済みの services/hubs と、チャープ WAV へのローカルアクセスが必要。
実機 ブラウザで評価モジュールが出力した参加 URL を開いて参加するスマートフォン・タブレット・ノート PC・HMD。インストール作業は不要で、chutvrc と評価モジュールの両方にネットワーク的に到達できることのみが要件。
参加者 / クライアント ルームに参加して評価モジュールに報告する側 (ボットユーザーまたは実機)。評価モジュールは client_id + label で識別する。
ブラウザエージェント chutvrc に組み込まれた小さな JS モジュール。?eval=1 付きでページが読み込まれた時のみ有効化される。評価モジュールと時刻同期したうえで、ポーズ・音声・RTC 統計をサンプリングし WebSocket で送出する。ボットユーザー (Puppeteer 経由) と実機は同一のブラウザエージェントコードを実行する。
セル 1 回の評価モジュール起動で計測される 1 件の (ホスティング × SFU × N) 構成。1 セルにつき eval/results/<run_id>/ ディレクトリが 1 つ生成される。
スピーカー / リスナー ブラウザエージェントの mode パラメータで指定する参加者のロール。1 セルにつきちょうど 1 名が speaker (マイクから音声レイテンシ計測用の 1 kHz チャープを送出)、それ以外は全員 passive リスナー。

推奨構成。 最もノイズの少ない計測を行うにはマシン 2 台構成を推奨:

  • マシン A: chutvrc サーバと評価モジュールホストを同一のマシンで走らせる。評価モジュールは受動的な WebSocket 収集プロセスで軽量であり、chutvrc と同居させることで --host-stats docker がリモート Docker の認証なしでローカルのコンテナ統計を読める。
  • マシン B: ボットユーザーホスト — スピーカーボットユーザーおよびリスナーボットユーザーを実行する。chutvrc ホスト上でボットユーザーを動かしてはならない。 同居させると (a) chutvrc と CPU/メモリを取り合って host.csv を汚染する、(b) chutvrc との通信が localhost / Docker ブリッジ経由になり、実クライアントの経路を反映しなくなる、(c) 評価モジュールとカーネルクロックを共有してしまうため時刻同期が見かけ上完璧に揃い、クライアント間レイテンシの計算にバイアスがかかる、という問題が発生する。

すべてを 1 台にまとめてよいのは初回スモークテスト (§2.4) のみで、計測本番のセルでは行わないこと。N ≥ 40 ではボットユーザーホストが複数必要になるので §3.4 の補足を参照。理想的にはスピーカー専用のボットユーザーホストを 1 台確保し、リスナーボットユーザーの CPU 負荷で chirp-emit のタイムスタンプがぶれないようにする。実機は上記いずれとも別のハードウェア。

コマンド枠のタグ。 本マニュアルの全コマンド枠には実行先を明示する:

  • 実行先: 評価モジュールホスト — eval-runner Docker コンテナを稼働させるマシン。
  • 実行先: ボットユーザーホスト — run-bot.js を起動するすべてのマシン。
  • 実行先: 任意のホスト — どこかでファイルを生成するだけの一度限りのセットアップ。生成物は必要な場所にコピーすればよい。

実機 (スマートフォン/タブレット/HMD) ではこれらのコマンドを実行しない。実機の役割はブラウザで URL を開くことのみである。

2. 評価の前に

2.1 ビルドとインストール

以下の各コマンドは特定のホストロールを対象とする。ハーネスを含む chutvrc-hubs-compose をクリーンな状態でクローンしたところから始める:

スピーカーボットユーザー用のサイレント・キャリア WAV を生成 (一度のみ)

実行先: 任意のホスト
node eval/assets/generate-chirp.js

eval/assets/chirp-loop.wav を生成する。スピーカーボットユーザーが動作するマシン (-a で指定) にこのファイルが必要。生成したマシンとは別のボットユーザーホストを使うなら、WAV をコピーするかそのマシンでスクリプトを再実行する。

eval-runner Docker イメージのビルド

実行先: 評価モジュールホスト
docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml build eval-runner

1 回ビルドすれば十分。eval/runner/ 配下のファイルが変わった時のみ再ビルドする。

ボットユーザーの Puppeteer インストールを検証

実行先: すべてのボットユーザーホスト
cd services/hubs/scripts/bot && npm install && node run-bot.js --help && cd -

run-bot.js を起動するすべてのマシンで実行する (高 N でボットユーザーを複数台に分散する場合は各マシンで実行)。Puppeteer の Chromium ダウンロードがブロックされる環境では PUPPETEER_DOWNLOAD_HOST を設定するか、別途 Chromium をインストールして Puppeteer から参照させる。Puppeteer のセットアップが成功していることが、ボットユーザー実行の前提条件となる。

2.2 ネットワークと時刻

  • 評価モジュールの設置場所を決める。すべての参加者 (実機・ボットユーザーホスト) から WebSocket で到達可能でなければならない。LAN 上なら評価モジュールホストの LAN IP もしくは mDNS 名 (hubs.local)。公衆インターネット経由ならリバースプロキシ + TLS 証明書を介する。
  • .env に EVAL_REPORT_HOST=<ホスト名または IP> を設定。compose ファイルがこれを使って参加 URL を組み立てる。
  • 計測に関わるすべてのホスト (評価モジュール、ボットユーザーホスト、できれば chutvrc サーバも) で NTP/chrony が動作していることを確認。LAN ではミリ秒未満、WAN でも 10 ms 未満であれば通常は許容範囲。実際の精度は run.json の clock-sync CI で確認できる。
  • LAN 上のスマートフォン/タブレット/HMD のブラウザから評価モジュールの WS ポート (デフォルト 9099) に到達できることを確認。ファイアウォールを開けておく。

2.3 SFU 認証情報 (Dialog 以外を計測する場合)

  • eval/.env.local (gitignore 対象) を作成し、Dialog 以外の各 SFU の認証情報を記載 (LiveKit API key/secret、Sora 署名鍵、Cloudflare Realtime app ID + secret)。
  • 同じ認証情報を管理パネルから reticulum の webrtc-settings にも反映する。稼働中のサーバが実際に参照するのはこちら。
  • 計測前に、各 SFU で手動でテストルームを開き、2 つの通常ブラウザ間で音声・映像が流れることを確認する。ハーネスは「観測される状態」をそのまま計測するため、バックエンド設定に誤りがあると、形式上は妥当でも意味のないデータが出力されてしまう。
課金リスク Sora と Cloudflare Realtime は従量課金。N=80 までスケールする前に各管理コンソールでレート制限と予算を確認すること。評価モジュールは Dialog 以外のセルで EVAL_ALLOW_BILLING=1 を要求するが、最終的な歯止めは人間の注意である。

2.4 初回スモークテスト (ラップトップで一度だけ実施)

実セルに着手する前に、全経路をエンドツーエンドで確認する。

1

使い捨てのターミナルで評価モジュールを起動

実行先: 評価モジュールホスト
docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml \
  run --rm --service-ports eval-runner start \
    --label smoke \
    --room https://hubs.local:4000/<any-test-room-sid> \
    --duration 90s \
    --dialog-url http://dialog:7001 \
    --host-stats docker \
    --public-url wss://${EVAL_REPORT_HOST:-hubs.local}:9099

評価モジュールが eval ブラウザエージェント用クエリ付きの参加 URL を出力する。--room の 4000 番はローカル開発用 hubs フロントエンドのポート。TLS で公開された hubs を使う場合はその URL (通常 443、省略可) に置き換える。--public-url の 9099 番は評価モジュール側の報告 WebSocket ポートで、hubs のホスティング形態にかかわらず常に 9099。

2

出力された URL をラップトップのブラウザで開く

出力された URL には &label=<device> が含まれているので、<device> を laptop-self に置き換える。DevTools のコンソールを開く。約 10 秒以内に次の行が出るはず: 

[eval] probe enabled mode=passive label=laptop-self report=wss://…
[eval] clock synced offset=…ms ±…ms

clock synced 行が現れないなら、WebSocket が評価モジュールに到達していない (ファイアウォール、ホスト名の誤り、TLS なし等)。先に進む前に解決すること。

3

評価モジュール終了を待ち、CSV を確認

90 秒後に評価モジュールが [runner] aggregator wrote CSVs to … を出力する。そのディレクトリ内で:

  • run.json にクライアント 1 件が記載され、clock_ci_ms < 5 であること。
  • probe-events.csv に rtc-stats 行 (ラップトップ自身の PC 統計) が含まれていること。
  • 他の CSV はピアもチャープもないため空でよい — 単独参加のスモークでは想定どおり。
4

スピーカーボットユーザーを加えた 2 クライアントスモーク

起動順が重要: 評価モジュール (報告 WS) を先に立ち上げ、その後にボット、最後にラップトップのブラウザを開く。ボットのプローブはページロード時に WS を一度開きにいくだけで、失敗してもリトライしない。

評価モジュールホストの 1 ウィンドウで評価モジュールを起動 (手順 1 と同じコマンド)。ボットユーザーホストの別ウィンドウで同じルームを向いたスピーカーボットユーザーを起動:

実行先: ボットユーザーホスト
cd services/hubs
EVAL_MODE=1 EVAL_LABEL=bot-speaker EVAL_SPEAKER=1 \
EVAL_REPORT_WS_URL=wss://${EVAL_REPORT_HOST:-hubs.local}:9099 \
node scripts/bot/run-bot.js \
  -o ${HUBS_HOST:-hubs.local:8080} \
  -r <room-sid> \
  -a ../../eval/assets/chirp-loop.wav

-o は /hub.html を配信するホストの hubs オリジンをポート込みで渡す (ボットは URL を https://<host>/hub.html として組み立てる)。docker-compose の開発スタックでは 8080 番 (hubs-client の webpack dev server)であり、4000 番 (reticulum, ルーム SID URL はブラウザに返すが /hub.html は 404) ではない。ローカル開発では -o hubs.local:8080 (もしくは export HUBS_HOST=hubs.local:8080) を指定する。デプロイ環境では /hub.html とルーム SID ルートを両方配信する単一オリジンを指定する。

ラップトップのブラウザから ?eval=1&mode=passive&label=laptop-self&report=… で同じルームに参加する。ルームページで少なくとも 1 度クリックすること (ロビーや入室手順自体にクリックが含まれていればそれで足りる) — Chrome の自動再生ポリシーにより、最初のユーザージェスチャまで チャープ検出器の AudioContext は suspended 状態のままで、URL を開いて放置するだけのタブでは chirp-detect = 0 になる。実行後、 probe-events.csv の laptop-self|chirp-detect 行と chirp-pairs.csv の両方に行があれば成功。空ならチャープの送受信経路に問題があるので §5 トラブルシューティング を参照してから続行。

実行中の簡易確認 (ラップトップのタブの DevTools コンソールで、ランナーがまだカウントダウン中に実行):

__eval.patcher._detector._ctx.state              // expect "running"
__eval.patcher._detector._activeDetectors.size   // expect >= 1 (リモート音声ピアの数)

2.5 マトリクスの計画

開始前にすべてのセルとそのラベルを決めておく。一貫したラベル体系を用意しておくと事後集計が容易になる。推奨方式: 

<hosting>+<sfu>+N<count>[+<variant>]
例:
  laptop+dialog+N10
  server+livekit+N40
  cloud+sora+N20+devices
  cloud+cloudflare+N80+bots-only

計測開始前に §4 のマトリクストラッカーを埋めておく。

2.6 ネットワーク選択 (方法論的注記)

ネットワークはマトリクスの制御軸ではないため、暗黙の定数として扱う:

  1. 1 セル 1 ネットワーク、全参加者を同一ネットワーク上に (ボットユーザー・実機・評価モジュール)。ネットワークを混在させると 1 行のレイテンシに複数の経路が混ざり、セル間の差を変化させた軸だけに帰属できなくなる。多くの SFU は最も品質の低いクライアントに合わせて適応するため、クライアント単位の切り分けも交絡したまま残る。
  2. 全マトリクスセルで同一ネットワークを使う。利用可能な中で最も安定したもの (通常はキャンパス所属者向け LAN) を選ぶ。ゲスト WiFi は UDP/STUN/TURN がしばしば遮断され WebRTC を破綻させるので避ける。
現実性 vs. 制御性。 単一 LAN 上で取得した制御マトリクスはベストケースの値であり、地理的に分散した実運用環境を反映していない。主マトリクスに混ぜるのではなく、別途実環境セルを 1〜2 件 (主にクラウドホスティング環境向けに) 追加し、参加者を自宅 / キャンパス / ゲスト網に分散させて実施し、結果は別個に報告する。厳密な均等配分ではなく代表性のあるカバレッジを目指す。デバイスはネットワーク別にラベル付けしておくと (mac-home-1, iphone-campus-2 等)、事後に pose-pairs.csv を home↔home, home↔campus 等のサブセットに切り分けられる。

セル内の運用ルール: 全参加者が chutvrc と評価モジュールの双方に到達できること (同一ネットワーク内のセルなら公開 DNS/TLS/VPN 構成は不要)。有線可能なホストは Ethernet 優先。バックグラウンド負荷の変動を避けるため、セル群はなるべく短時間内にまとめて実行する。

セルごとに記録する事項 (マトリクスのメモまたはラベル接尾辞 — +campus, +home, +mixed): クライアントのネットワーク、媒体構成、時間帯。

ネットワークごとに記録する事項 (1 度のみ、アイドル状態で、そのネットワーク上で計測セルを開始する前に — レイテンシ値の解釈に用いる):

項目 取得方法
名称 / 媒体 / リンク規格 SSID と WiFi 規格 (例: campus-eduroam, 802.11ax 5GHz) または有線リンク速度。macOS: system_profiler SPAirPortDataType。Linux: nmcli dev wifi, ethtool eth0。
chutvrc と評価モジュールへのベースライン RTT (平均 / 最小 / 最大 / 標準偏差) ping -c 30 <host>
経路 + ホップごとのロス mtr -rwc 30 <chutvrc-host> (もしくは traceroute)
上り / 下り スループット 両端を管理できるなら iperf3 -c <server>。できないなら speedtest-cli で概算。
UDP 許可 (+ ジッタ・ロス) iperf3 -c <server> -u -b 5M。UDP が遮断されると WebRTC は TURN-over-TCP にフォールバックしレイテンシが大幅に増えるため、その旨を明確に記録する。
STUN / TURN 到達性 + NAT タイプ https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/ を開き、srflx (STUN) と relay (TURN) の候補が現れることを確認。
外向きパブリック IP / ISP / 概略の地理的位置 curl ifconfig.me で IP を取得し、ipinfo.io/<ip> 等で ISP と位置を調べる。

実行中のストリーム単位 RTT・ジッタ・パケットロスは rtc-stats.csv に自動記録される。上記のアイドル時の計測は「SFU が遅い」のか「このネットワークが遅い」のかを切り分けるためのもの。

報告書では制約として明記する: マトリクスセルはネットワーク制御下での計測 (レイテンシの下限を与える) であり、実環境セルが現実的な範囲を示し、本番性能は各ユーザの経路に依存する。

2.7 事前チェックリスト (印刷してチェック)

  • eval/assets/chirp-loop.wav が存在する (node eval/assets/generate-chirp.js で生成)。
  • chutvrc-eval-runner Docker イメージがビルド済み (docker compose --profile eval … build eval-runner)。
  • ボットユーザーの Puppeteer インストールが正常に動作する (node scripts/bot/run-bot.js --help が終了コード 0)。
  • EVAL_REPORT_HOST を .env に設定済みで、全参加者デバイスから到達可能。
  • 評価モジュールホスト・ボットユーザーホストで NTP/chrony が稼働している。
  • マトリクスに含まれる各ホスティング環境について chutvrc のデプロイ手順を確認・テスト済み (セル種別ごとの詳細は §3.1 を参照)。
  • Dialog 以外の SFU を扱う場合: eval/.env.local と管理パネルの両方に認証情報を設定済みで、2 ブラウザでの手動疎通テストに通過済み。
  • 単独参加のスモークで生成された run.json の clock-CI が 5 ms 未満。
  • 2 クライアントスモーク (スピーカーボットユーザー + ラップトップ) で chirp-pairs.csv が空でない。
  • マトリクストラッカー記入済み: 全セルにラベルが付き、ラベルは全件で一意。
  • 最大 N に必要なボットユーザーホスト容量を確保 (ヘッドレス Chrome 1 個あたり約 250 MB のメモリ)。
  • 計測中、評価モジュール側 LAN に大きな同時転送等の負荷がないこと。
  • 計測ごとに 5 分のタイマー (もしくは --duration) を用意。

3. 各セルの実行中

マトリクスの全セルでこの手順を繰り返す。1 セルあたり手作業で約 10 分かかる。

3.1 セルの再構成 (手動)

1

ホスティング / デプロイ

セル種別に応じたデプロイ経路 (下表) で対象ホストに chutvrc を立ち上げる。動作確認: 通常のブラウザで通常のルームに参加し、マイクとポーズが機能していること。これはハーネス側で検証する事項ではない。デプロイそのものの動作が確認できるまで、ハーネスの出力を信用しないこと。

セル種別 必要なセットアップ 参照ドキュメント
laptop+* ローカルホスト上で docker-compose MANUAL_SETUP.md、SSL_SETUP.md、start-{linux,mac,windows}.{sh,command,bat}
server+* オンプレ Linux サーバ上で docker-compose MANUAL_SETUP.md、SSL_SETUP.md
cloud+* (compose) クラウド VM 上で docker-compose MANUAL_SETUP.md、SSL_SETUP.md
cloud+*+k8s k8s クラスタ (例: AKS) にマニフェストをデプロイ、Ingress + TLS、dialog Pod を hostNetwork 有効かつノードの公開 IP に一致する ANNOUNCED_IP で起動 k8s/docs/OVERVIEW.md、k8s/docs/BUILD_AND_DEPLOY.md、k8s/docs/COTURN_WEBRTC_FIX_PLAN.md

2 つのデプロイ経路の比較と推奨されるセル配置については eval/docs/deployment-comparison.md を参照。

2

SFU

管理パネル (https://<admin-host>:8989) で対象ルームを開き、SFU フィールドを次のいずれかに設定:

  • 0 Dialog
  • 1 Sora
  • 2 LiveKit
  • 3 Cloudflare Realtime

ブラウザ 1 つで参加し、DevTools の Network タブで期待する SFU の WebSocket/HTTP 通信が流れていることを確認する。SFU が誤っていれば計測結果は無意味になる。

3

ルーム状態のリセット

前回のランで残ったままになっている参加者をすべてキックする。評価モジュールはそれらのデータを集計対象には含めないが、残っていると SFU 負荷を歪める。管理パネルのキック操作を使うか、ルームを削除して再作成する。

3.2 評価モジュール起動

実行先: 評価モジュールホスト
docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml \
  run --rm --service-ports eval-runner start \
    --label "laptop+dialog+N40" \
    --room "https://${HUBS_HOST}/<room-sid>" \
    --duration 5m \
    --dialog-url http://dialog:7001 \
    --host-stats docker \
    --public-url "wss://${EVAL_REPORT_HOST}:9099"

評価モジュールはターミナルに接続したまま動作し続ける。出力された参加 URL をコピーする。5 分タイマーはこの時点から開始するため、手早く次の作業に進む。

評価モジュールが起動しないとき よくある原因は次の 2 つ: ポート 9099 が使用中 (前回の評価モジュールが正常終了していない)、または EVAL プロファイルが有効化されていない。docker ps で確認し、必要なら docker compose --profile eval … down で解消する。

3.3 スピーカー起動

次のいずれか1 つだけを選ぶ: スピーカーボットユーザー 1 台、または実機スピーカー 1 台。複数のスピーカーを同時に動かすのは不可 — 複数音源からのチャープは識別できない。

オプション A — スピーカーボットユーザー (ノイズの少ないセルにはこちらを推奨)

実行先: ボットユーザーホスト — chutvrc / 評価モジュールホストとは別のマシン 
cd services/hubs
EVAL_MODE=1 EVAL_LABEL=bot-speaker EVAL_SPEAKER=1 \
EVAL_REPORT_WS_URL="wss://${EVAL_REPORT_HOST}:9099" \
node scripts/bot/run-bot.js \
  -o "${HUBS_HOST}" \
  -r "<room-sid>" \
  -a ../../eval/assets/chirp-loop.wav &
スピーカーボットユーザーを chutvrc / 評価モジュールホスト上で起動しないこと。 同居させると (i) host.csv がボットユーザーの CPU/メモリを chutvrc 側の負荷として計測してしまい、(ii) ボットユーザーの WebRTC 通信が localhost を経由することになり、実クライアントの経路を反映しなくなり、(iii) 評価モジュールとカーネルクロックを共有することで時刻同期が見かけ上完璧に揃ってしまい、全クライアント間のレイテンシにバイアスがかかる。必ず別マシンを使うこと — ボットユーザー 1 台ならラップトップで十分 (約 250 MB のメモリ)。N ≥ 40 ではスピーカー専用のボットユーザーホストを 1 台割り当て、リスナーボットユーザーによる CPU 負荷で chirp-emit のタイムスタンプが遅れないようにする。

オプション B — 実機スピーカー

スピーカー用デバイス (スマートフォン/ラップトップ等の実機。上記コマンドを実行したホストとは別のもの) で評価モジュールの参加 URL を開き、&mode=passive を &mode=speaker に、&label=<device> を一意なスピーカータグ (例: &label=speaker-laptop) に書き換える。モバイル autoplay の制限を解除するため、ページを一度タップ/クリックする。

3.4 リスナーボットユーザー起動 (実機の数だけで N に届かない場合のみ)

実行先: ボットユーザーホスト (N ≥ 40 では複数台に分散) 
cd services/hubs
# 数を調整して目標 N に到達させる。
for i in $(seq 1 39); do
  EVAL_MODE=1 EVAL_LABEL="bot-listener-$i" \
  EVAL_REPORT_WS_URL="wss://${EVAL_REPORT_HOST}:9099" \
  node scripts/bot/run-bot.js \
    -o "${HUBS_HOST}" \
    -r "<room-sid>" \
    -a ../../eval/assets/chirp-loop.wav &
done

全ボットユーザーの参加完了まで約 30 秒待つ。評価モジュールは各ボットユーザーについて [runner] hello client_id=… label=bot-listener-N を出力する。起動したボットユーザー数より hello の数が少なければ起動に失敗したものがあるので、ボットユーザー側のターミナル出力を確認する。

複数ホストへのボットユーザー分散 N≥40 では 1 台ではメモリが不足しがち。SSH で 2 台目に接続し、同じ環境変数のまま同じループを実行する。評価モジュールは client_id + label で対応付けるので、それ以外に変更は不要。

3.5 実機の投入

各デバイスで以下を行う:

  1. QR を読み取るか、評価モジュールの参加 URL を開く。
  2. URL バーで &label=<device> を一意のタグに書き換える (例: quest3-haru, ipad-2-tabA, macbook-3-tabB)。タブごとに異なるラベルを付ける。
  3. ページを 1 度タップ/クリックして音声再生のブロックを解除する。
  4. デバイスのブラウザコンソール (または評価モジュール側ターミナル) でブラウザエージェントが [eval] clock synced を出力していることを確認する。

3.6 実行中の監視

実行中は以下を見守る:

  • 評価モジュール側ターミナル — 接続・切断がすべて想定通りであること。実行途中の切断は、多くの場合ボットユーザーのメモリ不足が原因。
  • 代表的なリスナー 1 台のコンソール — 約 30 秒ごとに [eval] clock re-validated が出続け、エラーが頻発していないこと。
  • chutvrc デプロイ全体の健全性 — dialog/reticulum コンテナが OOM-kill や再起動を起こしていないこと。docker stats または kubectl top pods で確認。

実行中に chutvrc・ネットワーク・他クライアントの設定を変更しない。途中で再構成するとそのセルは無効になる。異常があればメモを取る。

3.7 検証とアーカイブ

評価モジュール終了直後に eval/results/<run_id>/ を確認する:

セルごとの検証 (次セルを開始する前に実施)

  • run.json が存在し、clients 配列の長さが (スピーカー + リスナー + 実機) の合計と一致していること。欠けていればその参加者のデータが評価モジュールに届いていない。
  • clients 内の全エントリで clock_ci_ms < 5。これより CI が悪いセルは破棄を検討する。
  • どのエントリも warnings 配列が空であること。最も頻出する警告は "more than one mode=speaker" — これが出ていればそのセルのデータは汚染されているため再実行する。
  • pose-pairs.csv の行数は N × (N−1) × 4 × 67 × duration_sec × sample_rate に近くなるはず。5 分 N=10 dialog セル、sample_rate=1 で約 720,000 行。桁が合っていれば許容範囲。
  • chirp-pairs.csv の行数は (リスナー数) × (duration_sec / 1.5) 前後。期待値の 50 % 未満なら、一部のリスナーがスピーカーの音を拾えていない可能性があるため、結果を信頼する前に調査する。
  • host.csv に少なくとも dialog と reticulum (またはそれに相当するコンテナ) の行があること。空なら --host-stats の指定が誤っている。

結果ディレクトリは必要に応じてリネームする (デフォルトの <ISO-タイムスタンプ>_<label> でも内容を把握しやすい)。アーカイブ保管先にコピーまたは移動する — この CSV 群は以後の分析・レポートの一次データである。

マトリクストラッカー (§4) に run_id、CI、メモを追記する。

5. トラブルシューティング

ブラウザエージェントが "clock synced" を出さない

ブラウザエージェントは読み込まれているが評価モジュールに到達できていない。考えられる原因 (可能性の高い順):

  • &report= URL が誤っている。評価モジュールが出力した URL と照合する。
  • Mixed-content ブロック: https:// ページからは wss:// しか開けず、http:// ページからは ws:// しか開けない。TLS は全部か全くなしで揃える。eval-runner は起動時に EVAL_TLS_CERT / EVAL_TLS_KEY を読み、docker-compose.eval.yml でデフォルトは /certs/cert.pem + /certs/key.pem (services/hubs/certs/ をマウント) になっているため、ローカル開発では自動的に wss:// で待ち受ける。起動ログの [runner] report WS listening on wss://… を確認すること。(no TLS) と表示されていれば、証明書のパスが読めていない。
  • ブラウザが wss://<runner-host>:9099 の証明書を信頼していない。hubs ページが警告なしで開けているなら mkcert のルート CA は既に信頼されているはずで、同じ証明書で 9099 番も通る。それでも繋がらない場合は、ブラウザで https://<runner-host>:9099/ に一度アクセスして証明書例外を登録する (画面は "Upgrade Required" でよい — 重要なのは例外登録)。
  • CSP がレポート先のオリジンをブロックしている。reticulum は hub ページに厳格な Content-Security-Policy ヘッダを付与しており、connect-src に wss://<runner-host>:9099 が含まれていないとブラウザは WebSocket を開かない (DevTools に "Connecting to '…' violates the following Content Security Policy directive: 'connect-src …'" が出る)。ローカル開発では services/reticulum/config/dev.exs の websocket_hosts 文字列に追記し、reticulum を再起動して反映する。デプロイ環境では reticulum の admin 設定 (RetWeb.Plugs.AddCSP の custom rules) に追加する。
  • 評価モジュールホスト側でポート 9099 がファイアウォールに塞がれている。
  • k8s ingress 経由の場合: 証明書が信頼されていない、もしくは websocket トンネルのタイムアウトが短すぎる (haproxy のデフォルトは 60 秒、haproxy.org/timeout-tunnel: "30m" を設定)。

chirp-pairs.csv が空または極端に少ない

  • スピーカーが未接続、もしくは途中で落ちた。run.json で mode: "speaker" のクライアントを確認する。
  • スピーカーボットユーザーを EVAL_SPEAKER=1 なしで起動している — デフォルトのパッシブモードではチャープを送出しない。
  • モバイルのスピーカーで音声解除のタップを行っていない。mode=speaker はスマートフォン/タブレットでは適さない場合が多い — スピーカーボットユーザーを優先する。
  • コーデック劣化による Goertzel の検出漏れ。検証方法: 人間が同じルームに入り、周期的な 1 kHz の信号音が聴こえるか確認する。
  • チャープは聴こえるのに chirp-detect = 0 (probe-events.csv の emit は正常に出ているのに、すべてのリスナーで検出が 0)。検出器の AudioContext が Chrome の自動再生ポリシーで suspended のまま。プローブは最初の pointerdown / keydown / touchstart / click で自動的に resume するため、URL を開いて放置するだけのタブはこの状態に陥る。ルームページで一度クリックして再実行する。実行中に __eval.patcher._detector._ctx.state === "running" であることを確認するとよい。

pose-pairs.csv の行数が想定より大幅に少ない

  • リスナー URL に ?sample=<x> を付けたまま、期待値を x 倍に補正し忘れている。
  • ボットユーザーが途中で落ちた。ボットユーザー側のターミナル出力で process.exit、OOM、"Detected avatar dog-pile" の有無を確認する — 最後のメッセージは EVAL_MODE では continuing であるはず。Restarting となっていれば EVAL_MODE=1 付きで起動されていない。
  • 受信側サンプリングが有効になっている。ブラウザエージェントのデフォルトは sample=1.0 (100 %) だが、N ≥ 40 では WS の帯域削減のため sample=0.1 に下げる運用もある。

clock_ci_ms が大きい (> 5)

  • 評価モジュールホストに LAN 経由で ping を打ってみる。RTT > 5 ms であれば、それが計測可能な精度の限界となる。
  • 評価モジュールが WiFi 上にあるなら、評価中は Ethernet に切り替える。
  • 評価モジュールホストにバックグラウンドのネットワーク負荷がある — 同期処理、大容量ダウンロード、画面共有等を一時停止する。

評価モジュールが起動直後に "EADDRINUSE" で終了

ポート 9099 が既に使用中。占有しているプロセスを lsof -i :9099 (mac/linux) または netstat -ano | findstr 9099 (Windows) で特定して停止するか、--port 9100 を渡して別ポートで起動する (この場合 EVAL_REPORT_HOST 由来の URL も合わせて更新する)。

LiveKit / Sora で rtc-stats.csv にフィールドが欠落

ブラウザエージェントはアダプタの内部 (_sendTransport, room.engine.publisher.pc 等) に既知のフィールド名でアクセスする。上流アダプタの構造が変わっていれば PeerConnection リストが空になる。services/hubs/src/eval/rtc-stats.ts の extractPeerConnections を現在のアダプタのフィールドパスに合わせて修正する。他のメトリクスはそのまま動作し続ける。

6. 全セル完了後

評価モジュールコンテナを停止

実行先: 評価モジュールホスト
docker compose --profile eval -f docker-compose.yml -f docker-compose.eval.yml down

残ったボットユーザープロセスを停止

実行先: すべてのボットユーザーホスト
pkill -f run-bot.js

続けて以下を実施

  • 評価モジュールホスト上の eval/results/ ディレクトリ全体を長期保管先にアーカイブする。報告するあらゆる数値の一次データなので、それに見合った慎重さで扱う。
  • 作成した各図表・サマリーについて、eval/docs/figures-to-commands.md の該当行に run_id と実際に用いたコマンドを記入する。
  • eval/docs/interpreting-results.md の集計スニペットを全 run.json に対して実行し、セルごとのサマリー表を作成する。
  • CSV から好みのツール (matplotlib、R、ggplot、Excel など) でプロットを作成する。

8. 補足とスコープ判断

稼働中の SFU 切替は対象外

本評価ではルーム稼働中の SFU 切替を実施しない。各セルは評価モジュール起動前に reticulum で 1 つの SFU を設定して計測し、他の SFU への切替は稼働中のトグル操作ではなく、ルームを再構成 (§3.1) して新規セルとして始める。結果として:

  • reticulum の webrtc-settings|allow_switch_sfu フラグは本評価とは無関係であり、切替や復元の必要はない。
  • 本計測では chutvrc 内の動的再構成ロジックは検証されない。データから特徴づけられるのは (hosting, SFU, N) セルごとの定常状態における挙動のみである。

ハーネスの API 仕様と CSV カラム凡例は eval/docs/README.md および eval/docs/interpreting-results.md を参照。
